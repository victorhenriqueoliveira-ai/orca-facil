# ADR-003: Job de notificações diárias unificado em /api/cron/daily-notifications

## Status

Aceito

## Data

2026-07-25

## Contexto

A Fase 2 exige dois novos jobs de e-mail agendados: follow-up de orçamentos enviados sem resposta e aviso de orçamentos prestes a vencer. O padrão existente é um endpoint por cron (`/api/cron/trial-reminder`), autenticado por `CRON_SECRET` e declarado no `vercel.json`.

## Decisão

Criar **um único endpoint** `POST /api/cron/daily-notifications` que processa os dois novos tipos de notificação em sequência, dentro do mesmo handler. O `vercel.json` recebe uma segunda entrada de cron apontando para esse endpoint, mantendo o horário distinto do trial-reminder (ex.: `0 9 * * *`).

## Alternativas Consideradas

### Alternativa 1: Endpoints separados por tipo

- **Descrição**: `/api/cron/followup-reminder` e `/api/cron/expiry-reminder`, cada um com sua própria entrada no `vercel.json`.
- **Prós**: Isolamento de falha — se o follow-up falhar, o de vencimento ainda roda; mais fácil de re-executar manualmente um tipo só.
- **Contras**: Duas entradas no vercel.json; duas funções Vercel criadas; dois CRON_SECRET validations; lógica duplicada de autenticação e client Supabase.
- **Por que rejeitada**: Os dois jobs compartilham a mesma infraestrutura (Supabase service client, Resend client, autenticação CRON_SECRET). O ganho de isolamento não justifica a duplicação — os jobs rodam sequencialmente no mesmo handler, e um erro em um tipo não afeta o outro quando o handler trata erros por tipo.

## Consequências

### Positivas

- Uma única entrada no `vercel.json`.
- Código de autenticação e cliente Supabase compartilhados sem duplicação.
- Log unificado com summary de ambos os tipos.

### Negativas

- Se o handler tiver um erro fatal (ex.: CRON_SECRET ausente), ambos os tipos falham juntos.
- Re-execução manual requer lógica de filtro (query param `?type=followup`) para executar apenas um tipo.

### Riscos

- Timeout de função Vercel (default 10s para Hobby, 60s para Pro). Mitigação: processar cada tipo em lote com limite (ex.: 50 usuários por execução) e retornar 200 parcial se necessário.

## Notas de Implementação

Estrutura do handler:
```typescript
// POST /api/cron/daily-notifications
// 1. Validar CRON_SECRET
// 2. Processar follow-ups: buscar quotes com sent_at + followup_days <= now AND followup_notified_at IS NULL
// 3. Processar vencimentos: buscar quotes com (created_at + validity_days - 3 days) <= now AND status = 'sent' AND expiry_notified_at IS NULL
// 4. Retornar { followup: { sent, errors }, expiry: { sent, errors } }
```
