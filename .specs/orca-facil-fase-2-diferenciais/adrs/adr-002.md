# ADR-002: Alertas in-app como computed queries (sem tabela notifications)

## Status

Aceito

## Data

2026-07-25

## Contexto

O PRD exige alertas in-app para três eventos: aprovação do cliente via link, follow-up pendente após X dias e orçamento prestes a vencer. A decisão é se esses alertas vivem numa tabela dedicada (notifications) ou são derivados em tempo real consultando o estado atual dos orçamentos.

## Decisão

Implementar alertas in-app como **computed queries**: ao carregar o layout da aplicação, um único endpoint `GET /api/alerts` retorna os alertas ativos consultando a tabela `quotes` com filtros de estado. Nenhuma tabela nova de notificações é criada. O endpoint verifica:
- Orçamentos com `status = 'accepted'` nas últimas 48h → alerta de aprovação.
- Orçamentos com `status = 'sent'`, `sent_at` há mais de `profiles.followup_days` dias → alerta de follow-up.
- Orçamentos com `status = 'sent'`, vencendo em ≤ 3 dias → alerta de vencimento.

## Alternativas Consideradas

### Alternativa 1: Tabela notifications (polimórfica)

- **Descrição**: Job diário grava registros em `notifications(user_id, type, reference_id, read_at)`. Frontend consulta e marca como lidas.
- **Prós**: Histórico persistente de alertas; suporte a "marcar como lido" permanente; extensível para push notifications futuras.
- **Contras**: Nova tabela + RLS + índices; job diário precisa gravar E o frontend precisa consumir; duas fontes de verdade (quote status + notification status).
- **Por que rejeitada**: O estado dos orçamentos já contém toda a informação necessária. Uma tabela de notificações adiciona complexidade sem acrescentar dado novo — é duplicação de estado derivável.

### Alternativa 2: Flags por orçamento (followup_notified_at, expiry_notified_at)

- **Descrição**: Campos timestamp na tabela `quotes` indicam quando cada alerta foi disparado. Frontend filtra orçamentos onde o campo está nulo (alerta ainda não visto).
- **Prós**: Rastreia se o e-mail foi enviado e se o alerta in-app foi exibido, sem tabela nova.
- **Contras**: Mistura responsabilidade de notificação no modelo de orçamento; difícil estender para novos tipos de alerta.
- **Por que rejeitada**: Os campos `followup_notified_at` e `expiry_notified_at` ainda são necessários na tabela `quotes` — mas apenas para controle de deduplicação de e-mail no cron, não para renderização in-app.

## Consequências

### Positivas

- Zero tabelas novas para esta funcionalidade.
- Alertas sempre consistentes com o estado real dos orçamentos (sem stale data).
- Implementação em um único Route Handler.

### Negativas

- Sem histórico de alertas; se o marceneiro dispensar um alerta, ele some (não há "marcar como lido" persistente).
- O endpoint `GET /api/alerts` é chamado em cada carregamento do layout — deve ser leve (query simples indexada, sem JOINs pesados).

### Riscos

- Se o número de orçamentos crescer, a query pode ficar lenta sem índice adequado. Mitigação: índice em `(user_id, status, sent_at)` cobre os três filtros.

## Notas de Implementação

O endpoint `GET /api/alerts` retorna JSON com arrays separados por tipo: `{ approved: [...], followup: [...], expiring: [...] }`. O componente de layout do `(app)` faz fetch desse endpoint e exibe badges/banners. Cada item do array contém `quote_id`, `quote_number`, `customer_name` e `action_url` para navegação direta.
