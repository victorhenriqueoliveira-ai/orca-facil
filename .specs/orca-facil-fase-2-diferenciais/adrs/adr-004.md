# ADR-004: Geração do approval_token integrada ao PATCH de status 'sent'

## Status

Aceito

## Data

2026-07-25

## Contexto

O link de aprovação requer um token UUIDv4 único por orçamento. O token precisa ser gerado em algum momento do fluxo — ao mudar o status para 'sent', ao gerar o PDF, ou em endpoint dedicado. A escolha define o contrato de API e a atomicidade da operação.

## Decisão

Gerar o `approval_token` **automaticamente** dentro do handler `PATCH /api/quotes/[id]` quando o campo `status` for alterado para `'sent'`. O handler verifica se já existe um token (para não sobrescrever em re-envios); se não existir, gera um `gen_random_uuid()` e persiste junto com `approval_token_expires_at = created_at + validity_days`. O token gerado é retornado no response do PATCH para uso imediato pelo frontend.

## Alternativas Consideradas

### Alternativa 1: Endpoint dedicado POST /api/quotes/[id]/send

- **Descrição**: Novo endpoint que combina: mudar status para 'sent' + gerar token + retornar link. PATCH /api/quotes/[id] não gera token.
- **Prós**: Semântica explícita de "envio"; fácil de testar isoladamente; separa "salvar status" de "ativar link de aprovação".
- **Contras**: Novo arquivo de rota; o marceneiro pode mudar status para 'sent' via PATCH sem gerar token (inconsistência); dois endpoints para o mesmo ato.
- **Por que rejeitada**: O frontend já usa PATCH /api/quotes/[id] com `{ status: 'sent' }` na etapa 4 do wizard. Introduzir um novo endpoint exigiria refatoração do wizard sem ganho real de isolamento.

### Alternativa 2: Geração ao gerar o PDF (POST /api/quotes/[id]/pdf)

- **Descrição**: O token é gerado e persistido junto com o PDF, retornado no response do endpoint de PDF.
- **Prós**: Um orçamento só tem link de aprovação quando tem PDF — consistência lógica.
- **Contras**: O marceneiro pode gerar múltiplos PDFs (modo summary + detailed), cada geração sobrescreveria o token; PDFs podem ser gerados sem intenção de envio imediato (preview).
- **Por que rejeitada**: A geração de PDF é uma operação de leitura/renderização, não de mudança de estado. Misturar geração de token nela viola SRP e cria comportamento surpreendente ao gerar PDF para visualização.

## Consequências

### Positivas

- Zero endpoint novo para esta funcionalidade.
- Token gerado atomicamente na mesma transação que muda o status.
- Response do PATCH já retorna `{ approval_link, approval_token }` — frontend usa sem chamada extra.

### Negativas

- O PATCH /api/quotes/[id] passa a ter comportamento condicional (gera token se status='sent') — precisa de documentação clara no código.
- Re-envio (PATCH com status='sent' quando já é 'sent') deve reusar o token existente, não gerar novo.

### Riscos

- Race condition em re-envios paralelos (improvável em uso real mobile). Mitigação: verificar `approval_token IS NULL` antes de inserir; usar `UPDATE ... WHERE approval_token IS NULL` para evitar sobrescrita.

## Notas de Implementação

```typescript
// Dentro do PATCH handler, após validar status='sent':
if (status === 'sent') {
  const { data: existing } = await supabase
    .from('quotes').select('approval_token').eq('id', quoteId).single()
  
  if (!existing?.approval_token) {
    const expiresAt = /* created_at + validity_days */
    await supabase.from('quotes').update({
      approval_token: crypto.randomUUID(),
      approval_token_expires_at: expiresAt,
      sent_at: new Date().toISOString(),
    }).eq('id', quoteId).is('approval_token', null)
  }
}
```
