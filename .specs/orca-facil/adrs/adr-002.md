# ADR-002: Puppeteer + @sparticuz/chromium para Geração de PDF

## Status

Aceito

## Data

2026-07-20

## Contexto

O PRD exige geração de PDF server-side com visual consistente em qualquer dispositivo. A aplicação roda em Next.js na Vercel (funções serverless). O PDF precisa suportar logo da marcenaria, tabelas dinâmicas de itens, layout responsivo e eventual adição de fotos na Fase 2.

Três abordagens foram avaliadas para a geração de PDF no Route Handler Next.js.

## Decisão

Usar **Puppeteer** com **@sparticuz/chromium** (build otimizado para AWS Lambda / Vercel serverless). O fluxo: montar HTML com CSS (usando os mesmos tokens de design do Tailwind via classes inline ou CSS embutido) → lançar browser headless → `page.pdf()` com formato A4 → armazenar no Supabase Storage → retornar URL assinada.

## Alternativas Consideradas

### Alternativa 1: @react-pdf/renderer

- **Descrição**: Biblioteca React que renderiza PDFs diretamente no servidor usando primitivas próprias (View, Text, Page).
- **Prós**: Sem dependência de browser, leve para funções serverless, zero overhead de Chromium (~50MB).
- **Contras**: Layout com primitivas proprietárias, sem suporte a Tailwind. Toda estilização precisa ser reescrita em StyleSheet próprio. Curva de aprendizado separada do restante do projeto.
- **Por que rejeitada**: O custo de manter dois sistemas de layout (Tailwind para o app, StyleSheet para PDF) supera o ganho de leveza.

### Alternativa 2: pdf-lib + templates estáticos

- **Descrição**: Geração programática de PDF sobre template base (coordenadas fixas).
- **Prós**: Controle total sobre cada pixel, zero browser, ultra-leve.
- **Contras**: Extremamente verboso para PDFs com número dinâmico de linhas. Cada mudança de layout requer recálculo manual de coordenadas.
- **Por que rejeitada**: Inviável para PDF com número variável de ambientes, itens e variantes.

## Consequências

### Positivas

- Visual pixel-perfect, idêntico ao que o marceneiro veria num browser real.
- Reutiliza a mesma linguagem de estilização (classes CSS/Tailwind inline) do restante do app.
- Fácil adicionar fotos, renders ou elementos visuais ricos na Fase 2 sem mudar a abordagem.

### Negativas

- @sparticuz/chromium adiciona ~50MB ao bundle da função serverless. A Vercel suporta funções de até 250MB na camada Pro, mas é o componente mais pesado do projeto.
- Tempo de inicialização a frio (cold start) da função de geração de PDF pode ser de 2–5s na primeira invocação. Invocações subsequentes reusam o processo.
- Limite de duração de função na Vercel: 60s no plano Hobby, 300s no Pro. Para o volume esperado no MVP, 60s é suficiente.

### Riscos

- **Risco**: atualização de @sparticuz/chromium pode quebrar compatibilidade com Puppeteer. Mitigação: fixar versões no package.json e atualizar intencionalmente.
- **Risco**: cold start lento impacta UX percebida. Mitigação: mostrar loading state claro com estimativa de tempo ("Gerando PDF...") e habilitar keep-warm via cron se necessário na Fase 2.

## Notas de Implementação

- Instalar: `puppeteer-core` + `@sparticuz/chromium`
- Configurar `executablePath` dinamicamente: local usa `puppeteer` padrão, produção usa `chromium.executablePath()`
- A função de PDF deve rodar como Route Handler (`/api/quotes/[id]/pdf`) com `export const maxDuration = 60`
- Definir `export const runtime = 'nodejs'` no Route Handler (não Edge)
