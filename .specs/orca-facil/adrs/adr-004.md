# ADR-004: Templates do Sistema Armazenados no Postgres com Seed

## Status

Aceito

## Data

2026-07-20

## Contexto

O produto oferece templates pré-definidos por ambiente (cozinha, quarto, sala, etc.) com listas padrão de materiais e serviços. Esses templates precisam ser mantidos e corrigidos ao longo do tempo (ex.: adicionar item faltante, corrigir nome, ajustar quantidades padrão). A questão é onde armazenar esses dados.

## Decisão

Templates do sistema ficam em tabelas Postgres (`system_templates` e `system_template_items`), populadas via **migration de seed** no Supabase. Correções e adições de templates são feitas via SQL (nova migration ou UPDATE direto no painel Supabase) sem necessidade de deploy de código.

## Alternativas Consideradas

### Alternativa 1: Arquivo TypeScript estático (constante no código)

- **Descrição**: Templates definidos como array de objetos TypeScript no repositório (ex.: `lib/templates.ts`).
- **Prós**: Versionados junto com o código, sem dependência de migration.
- **Contras**: Qualquer correção de template exige commit + deploy na Vercel. Não permite edição de emergência em produção.
- **Por que rejeitada**: Para um desenvolvedor solo, a capacidade de corrigir um template errado em produção sem passar pelo ciclo de deploy é valiosa, especialmente logo após o lançamento.

## Consequências

### Positivas

- Templates podem ser corrigidos ou expandidos em produção via painel Supabase sem novo deploy.
- Mesma fonte de dados para todos os usuários, garantindo consistência.
- RLS pode ser configurado para `SELECT` público (todos os usuários autenticados) e `INSERT/UPDATE/DELETE` bloqueado via RLS (somente service role ou admin).

### Negativas

- Templates não são versionados automaticamente com o código-fonte. Mudanças feitas diretamente no banco precisam ser documentadas como migrations retroativamente.
- Requer seed inicial como parte do setup do ambiente de desenvolvimento.

### Riscos

- **Risco**: Inconsistência entre ambiente de dev e produção se o seed não for mantido atualizado. Mitigação: seed via arquivo SQL de migration versionado no repositório (`supabase/seed.sql`).

## Notas de Implementação

- Criar `supabase/seed.sql` com os INSERTs iniciais dos templates.
- RLS em `system_templates`: `CREATE POLICY "read_all" ON system_templates FOR SELECT TO authenticated USING (true);`
- RLS em `system_template_items`: mesma política de leitura pública para autenticados.
- Nenhuma operação de escrita nessas tabelas via código da aplicação — somente leitura.
