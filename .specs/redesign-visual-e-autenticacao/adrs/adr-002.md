# ADR-002: Substituição de OTP por Email+Senha via Supabase signInWithPassword

## Status

Aceito

## Data

2026-07-22

## Contexto

O Orca Fácil usa `supabase.auth.signInWithOtp()` com verificação em `/verify`. Usuários existentes foram criados via OTP — sem senha definida. A decisão de produto é substituir OTP completamente por email+senha. O Supabase Auth suporta ambos os métodos, mas não expõe programaticamente se um usuário "tem senha ou não" — `signInWithPassword` retorna o mesmo erro genérico para senha errada e para usuário sem senha.

## Decisão

Substituir as páginas `/login` e `/verify` por fluxo email+senha usando:
- `supabase.auth.signUp()` para cadastro
- `supabase.auth.signInWithPassword()` para login
- `supabase.auth.resetPasswordForEmail()` para reset (e como caminho de migração para usuários OTP)
- `supabase.auth.updateUser({ password })` para definir nova senha após clicar no link

Migração de usuários existentes: ao falhar login com `signInWithPassword`, exibir mensagem orientando a usar "Esqueci minha senha" para definir uma senha pela primeira vez. O fluxo de reset é tecnicamente idêntico ao de primeira definição de senha.

A rota `app/api/auth/callback/route.ts` (existente) é reaproveitada para processar o token de reset via `exchangeCodeForSession`.

## Alternativas Consideradas

### Alternativa 1: Manter OTP como opção alternativa + adicionar email+senha

- **Descrição**: Duas opções de login coexistem.
- **Prós**: Sem quebra para usuários existentes.
- **Contras**: UX mais complexa; manutenção de dois fluxos; o OTP é a dor que o usuário quer eliminar.
- **Por que rejeitada**: Decisão de produto confirmada pelo usuário — substituição completa.

### Alternativa 2: Implementar autenticação própria (sem Supabase Auth)

- **Descrição**: Hashing de senha manual, JWT próprio.
- **Prós**: Controle total.
- **Contras**: Responsabilidade de segurança, complexidade, fora das restrições do PRD.
- **Por que rejeitada**: Violaria constraint do PRD ("usar Supabase Auth para toda a camada de autenticação").

## Consequências

### Positivas

- Login determinístico (sem depender de entrega de email/SMS externo para cada acesso).
- Fluxo de reset reaproveitado como caminho de migração — sem código extra.
- Callback route existente reutilizada sem mudança de contrato.

### Negativas

- Usuários existentes precisam passar pelo fluxo de reset para definir senha — atrito pontual na migração.
- Impossível distinguir programaticamente "senha errada" de "sem senha" — mensagem de erro deve orientar para o reset.

### Riscos

- **Risco**: Usuário existente com telefone como identificador (sem email) não consegue usar reset por email. **Mitigação**: verificar na tabela `auth.users` antes da release se há usuários com `email IS NULL`; tratar como caso especial (suporte manual).
